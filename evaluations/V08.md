# Conceptualize V0.8 — Context Capability

## Status

The product-side V0.8 changes are implemented locally: the public interaction is described as `@Conceptualize` plus an ordinary task, the default MCP primitive accepts only that task, and the runtime compiles selected evidence into provenance-preserving Working Context sections. The primary effectiveness/economics comparison is **blocked by invalid baseline grading**. No activated-model result is claimed, and this is not a completed V0.8 evaluation.

## Product and agent interface

The product separates three layers:

- User: activate Conceptualize for a normal task using the host's native capability mechanism; mention syntax is a product convention, not a runtime parser.
- Agent: one read-only default MCP capability with a single required `task` field. The user task is passed through unchanged.
- Runtime: ContextUnits, relationships, deterministic classification, source state, the session ledger, Working Context/Delta, and full trace diagnostics.

The concise server instructions tell the agent to use Conceptualize only when activated, keep the user's task primary, avoid retransmitting supplied context, prefer current information over explicitly superseded information, and continue with normal reasoning and tools. The tool description presents context augmentation as the capability rather than asking the model to choose a retrieval strategy. No source, budget, mode, or refresh parameters appear in the default schema. The six legacy operations remain behind the existing advanced/debug opt-in.

The tool maps `task` to the internal runtime's existing context query. The compact model response remains context, new-context token count, previous-context reuse, source names, and trace ID. Full candidate scores, provenance, relationships, timings, and ledger details remain in the persisted trace.

## Working Context

The V0.7 package delivered 22/23 frozen fact alternatives, while its model answers still failed. V0.8 changes representation without adding an internal model or rewriting source evidence. Selected units are grouped under only the sections that contain them: current decisions, constraints, current implementation state, relevant source context, and relevant context. Each original unit remains verbatim with a source header. A trace-side `working_context` entry records unit ID, source ID, category, classification origin, and explicit relationship origins.

Classification uses explicit metadata first, explicit declared relationships second, then small deterministic wording rules. Anything unmatched remains relevant context. These rules label source evidence; they do not synthesize decisions or summaries. Existing session-delta behavior remains in place: unchanged units are referenced in the ledger and omitted from the next context string.

The fixture-backed package selected 49 of 101 candidates and compiled 3,605 cl100k tokens from 8,167 available history tokens (44.14%). Candidate context was 6,506 tokens; 2,866 low-relevance tokens and 107 explicitly superseded tokens were omitted. The frozen alternatives detect 7/7 facts in the compiled package. This is a deterministic selection diagnostic only; it does not establish model correctness or provider-token savings. Full data is in [context-engine results](results/v08-context-engine.json).

A separate deterministic follow-up requested sync recovery and browser permission behavior. Its first context was 3,605 tokens; the follow-up returned 522 new tokens, referenced 19 previously delivered units, and avoided retransmitting 1,580 unchanged tokens. No model was called, so provider input is unavailable. See [session-delta results](results/v08-session-delta.json).

## Decision and remaining work

All four frozen baseline attempts failed their predeclared pass-rate gates. The activated condition, provider-token comparison, and any V0.8 effectiveness or efficiency conclusion remain unmeasured.
