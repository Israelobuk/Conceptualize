# Conceptualize V0.6 — Invisible Context Runtime

## Result

V0.6 delivers a single primary MCP operation, a deterministic internal planner, session-aware context deltas, conversation redundancy suppression, explicit provenance-bearing relationships, conversation-only source freshness, and separate model-facing and trace payloads. It does **not** demonstrate an end-to-end model-token or speed improvement. The central finding is that enabling autonomous MCP in the tested Codex host adds far more provider-reported input than the local MCP surface and returned context can account for.

No AI model, embedding, vector database, semantic reranker, or model API runs inside Conceptualize. The real-model benchmark uses an external Codex CLI only to evaluate host integration.

## Primary interface and MCP surface

Normal MCP configuration exposes only `conceptualize_context(query, token_budget?, source_types?, force_refresh?)`. The default instructions recommend one call with the task and its specific entities. The runtime determines sources, resolves explicit targets, follows repository graph or explicit conversation relationships, ranks and bounds candidates, and returns a compact context delta. The six advanced operations and capability resource are opt-in with `CONCEPTUALIZE_MCP_ADVANCED=true`.

The V0.5 source at the existing commit was profiled from a temporary snapshot: its six-tool stdio surface measured 1,466 `cl100k_base` tokens and 7,126 serialized bytes across initialization, tool listing, and resources. V0.6's one-tool default measured 277 tokens and 1,297 bytes, an 81.1% reduction in this local estimate. V0.6's seven-tool advanced/debug surface measured 1,545 tokens and 7,453 bytes; the V0.6 default listing alone is 161 estimated tokens, server instructions 38, and capability resource 14. These are local serialization estimates, not provider-measured prompt costs. See the [V0.5 profile](results/v05-mcp-surface.json), [V0.6 surface comparison](results/v06-mcp-surface.json), [default raw profile](results/v06-mcp-surface-default.json), and [advanced raw profile](results/v06-mcp-surface-advanced.json).

## Context engine, retrieval, and session evidence

The frozen six-case deterministic suite passed all six required-fact/file checks. It covers conversation continuity, a shared contract with a hidden consumer and test, session continuation, topic shift, explicit supersession, and a one-file negative control. Across those cases it recorded 271 candidate tokens, 182 selected tokens, 20 duplicate tokens suppressed, and two superseded units suppressed. The follow-up session call returned zero new context tokens and referenced unchanged earlier context. Source messages remain stored; suppression only changes package selection. Full scores, candidate decisions, and contexts remain in the trace/evaluation outputs. Results: [context engine](results/v06-context-engine.json), [session delta](results/v06-session-delta.json), [redundancy](results/v06-redundancy.json), and [frozen fixtures](v06/fixtures.json).

On the 39-message frozen conversation, the complete user task produced 100% exact required-fact availability in 677 context-string tokens (16 selected messages from 23 lexical/decision candidates), compared with 1,046 full-history tokens. Neither of the marked unrelated messages appeared. The model-generated query observed in autonomous Mode C also exposed all checked facts, in 727 tokens across 17 selected messages. This measures retrieval availability, not model answer correctness. It is not a general compression guarantee. See [conversation retrieval](results/v06-conversation-retrieval.json).

## Three-mode model-context economics

All three modes use the same frozen 39-message conversation, question, `gpt-6-sol` model ID, Codex CLI `0.158.0-alpha.2.1`, and exact-term rubric. Each primary mode has one run; results are exploratory.

| Mode | Context path | Pass | Input tokens | Cached input | Output | Context delivered | End-to-end elapsed |
| --- | --- | ---: | ---: | ---: | ---: | ---: | ---: |
| A | Full history, no Conceptualize MCP | No | 15,781 | 8,320 | 305 | 1,671 full-history context tokens | 10.89 s |
| B | Precompiled Conceptualize package, MCP hidden from model | No | 14,823 | 12,032 | 268 | 693 package tokens | 11.56 s |
| C | Autonomous MCP available and invoked once | No | 94,943 | 82,688 | 505 | 743 context tokens; 900 tokens in the serialized Codex result text | 21.67 s |

All three answers failed the frozen all-checks rubric. Exact-string coverage was 77.78% in A and 77.78% in B; C reached 88.89%, but also failed. B reduced provider input by 958 tokens (6.1%) versus A on this one run, while increasing end-to-end elapsed time by about 0.67 seconds. It is suggestive, not evidence of a repeatable benefit. The deterministic context report and model answer report use separate checks; selected context availability must not be mistaken for model correctness.

The paired A/B records both pass 14 of 18 exact-term checks, but fail different checks: A omits the resumable SyncEngine/next-step details and the no-websocket phrase; B omits retry policy, no-websocket, plain-text, and explicit out-of-scope terms. The 693-token B context contains the relevant history; these are answer omissions under a wording-sensitive rubric, not proof those facts were absent from the package. Still, because neither answer passes, V0.6 does not establish lower input while preserving task correctness. For this model fixture, A's available full history was 1,671 context tokens by the agent benchmark's tokenizer; B compiled 693; C returned 743 context tokens (900 tokens for serialized result text). Separately, the retrieval diagnostic counts message content without the same wrapper/prompt serialization: 1,046 full-history tokens and 677/727 selected tokens. Do not compare those diagnostic counts as provider input or substitute them for the A/B/C measurements.

The primary C run made one `conceptualize_context` call. Its argument object was 247 bytes. The Codex event's serialized result object was 8,347 bytes; the MCP text response itself can appear beside a structured copy in that event, so this event serialization size is not claimed as on-wire size or unique model-visible bytes. The model-facing context string was 743 tokens, while the compact JSON response text measured 900 tokens. The complete source trace is preserved separately from the compact model response. See the [three-mode results](results/v06-three-mode.json), [MCP integration measurements](results/v06-mcp-integration.json), and ignored raw runs referenced there.

An additional no-adoption C probe made zero Conceptualize calls and returned zero context, yet used 45,976 input tokens versus the paired Mode A run's 15,781 (+30,195). In the invoked C run, the increase over A was 79,162 input tokens. The measured serialized default MCP surface is 277 estimated tokens, so the local surface alone cannot explain either delta. Provider telemetry is turn-aggregate: it does not expose the internal Codex prompt or MCP-integration components. The exact supported attribution is therefore **MCP-enabled autonomous Codex host execution**, with 29,918 tokens unexplained beyond the local surface estimate in the no-adoption probe. It is not Conceptualize's selected context alone. This is a serious integration cost, not hidden or normalized away.

Compared with the V0.5 six-tool interface, the V0.6 default exposes only the primary context operation and leaves six legacy/debug definitions opt-in. In the observed V0.5 gpt-6-sol runs, one used `map` plus `expand` (two calls) and another used `pack` (one call); V0.6's observed run used one `conceptualize_context` call. This is a smaller default surface and fewer calls in the multi-step observation, but the one-run sample and large MCP-enabled host token increase do not show lower provider overhead.

## Runtime overhead

The invoked C request ran with SQLite and Redis deliberately unavailable in the isolated local evaluation. The persisted API trace measured 261.2 ms total: 220.8 ms cache connection timeout, 16.9 ms context compilation, 11.6 ms scoring, 4.2 ms source load, 3.4 ms trace write, and 0.09 ms graph build. Git analysis was 0 ms for the conversation-only request. The cache has a five-second failure cooldown; a healthy Redis instance should avoid this specific timeout. This local trace is not a production performance estimate. Pure MCP HTTP transport and stdio startup per model tool call are not exposed in the Codex event telemetry; MCP stdio discovery/startup is captured separately in the surface profile. No runtime optimization was made that weakens correctness to improve the model benchmark.

## Source freshness and session behavior

`/v1/runtime` infers or accepts requested source types before doing freshness work. Conversation-only requests load conversation units without repository indexing or graph refresh; a repository request retains its existing repository freshness/index path. The API test prevents `index_project` from being called for a conversation-only request. Session deliveries retain content hash, version, supplied operation, query, ranges, relationships, timestamps, and invalidation state. The compact MCP response returns context, new-context token estimate, session reuse flag, represented sources, and trace ID; detailed scoring and selection remain in API traces.

Conversation adapters preserve explicit relationship metadata such as `supersedes`, `updates`, `contradicts`, and `references`, with origin and heuristic labels. Deterministic text similarity suppresses exact, quoted, contained, and high-overlap duplicates without deleting source records. Low-information acknowledgements and low-relevance lexical candidates have explicit trace omission reasons. No unsupported semantic contradiction inference is claimed.

## Reproduction

Run deterministic suites and local MCP surface profiles:

```powershell
.venv\Scripts\python.exe -m conceptualize_evaluation.v06_context_benchmark
.venv\Scripts\python.exe -m conceptualize_evaluation.conversation_retrieval_v06
.venv\Scripts\python.exe -m conceptualize_evaluation.surface --python .venv\Scripts\python.exe --output evaluations\results\v06-mcp-surface-default.json
.venv\Scripts\python.exe -m conceptualize_evaluation.surface --python .venv\Scripts\python.exe --advanced --output evaluations\results\v06-mcp-surface-advanced.json
```

The real-model runner accepts `mode_a_full_context`, `mode_b_precompiled`, and `mode_c_autonomous_mcp` through `--conditions`. Supply the same frozen fixture/model, an isolated Codex home, a local API/database containing that conversation, and a project key. Run modes into fresh output directories; do not overwrite raw evidence. `v06_assemble` builds the tracked summaries from those run directories. No cost is estimated without a pricing snapshot.

## Limits and conclusion

One task/model/repetition cannot estimate general correctness, speed, adoption, or cost. Exact phrase matching is wording-sensitive. The local MCP surface estimate is not a Codex prompt token count. The host currently adds a large, internally unattributed input cost when MCP is configured, whether the tool is used or not. Consequently, this phase proves the unified interface, deterministic context behavior, and session delta on its fixtures, but it does **not** meet the end-to-end model-context economics criterion. The next technical priority is to isolate and remove that Codex MCP-enabled host cost before making token- or speed-saving claims.
