# Conceptualize V0.9 — Capability Effectiveness

## Decision

**Outcome E: baseline invalid for the A/B gate.** The frozen semantic evaluator judged the normal full-context agent at **0/3**. Each answer omitted the same required architecture proposition: that local persistence and synchronization are independently replaceable layers. The answer named LocalStore and SyncEngine and described their responsibilities, but did not state the replaceability decision. This is a substantive omission under the frozen task and rubric, not an exact-wording or heading mismatch. Per the predeclared rule, the `@Conceptualize` condition was not run. V0.9 therefore makes no claim about capability effectiveness, model utilization, or context sufficiency.

V0.8's product implementation remains unchanged. V0.8 established the task-only capability interface and Working Context/Delta, but its lexical benchmark could not establish effectiveness. V0.9 preserves that record and uses an external semantic evaluator; the Conceptualize runtime still has no model dependency.

The external evaluator is `gpt-6-astra`, low reasoning, through Codex CLI 0.157.1. Answer generation uses `gpt-6-sol`, low reasoning, through the same CLI. The CLI does not expose a temperature setting; none is claimed. The judge receives only the task, frozen propositions/pass criteria, a neutral answer ID, and the artifact. It returns proposition-level `present`, `absent`, `contradicted`, or `stale_as_current` statuses with short answer quotations and reasons, plus coverage and pass/fail. It receives no condition labels, model usage, tool events, or runtime trace.

The corrected synthetic reliability suite passed **8/8** before the baseline. ## Activated condition and interpretation

**Not run.** The activated condition requires a baseline of at least 2/3; the observed 0/3 failed that gate. There are no V0.9 `@Conceptualize` model answers, capability-call counts, Working Context grades, context-delivery averages, or activated-condition telemetry. The missing replaceability proposition cannot be classified as a Conceptualize retrieval or model-utilization failure because the capability condition was never exercised.

The frozen criterion exposed a repeatable gap in normal-agent recovery of an architecture decision, despite that decision appearing in the full history. This makes the baseline task unsuitable for the requested comparative claim at this strict pass threshold. The correct next step is to retain the V0.9 result as a failed baseline gate; no post-answer rubric or task changes were made, and no V0.10/economics phase is started here.

## ARCH_02 root-cause diagnostic (2026-09-29)

This is a post-baseline diagnostic using the frozen V0.9 fixture, ground truth, evaluator prompt, and `gpt-6-sol` low reasoning configuration. It does not change or regrade the original V0.9 baseline evidence above.

The missing decision is explicit in four messages: `h03` (#3, about 0.99% through the 8,292-token history), `h04` (#4, 1.60%), `v07-042` (#41, 21.90%), and `v07-043` (#42, 23.24%). The first and later user statements directly say the local-persistence and synchronization layers can be replaced independently; the assistant messages repeat that they are independently/separately replaceable. The PWA decision supersedes the initial native-client proposal, not this layer boundary. No later message contradicts or supersedes it. Later messages add detail about storage backends and SyncEngine responsibilities. The final handoff at #119 (98.49%) focuses on unfinished attachment work and does not repeat this specific proposition.

The baseline prompt artifacts include the complete 119-message history; no truncation was found. The relevant statement is early and repeated. Provider cache telemetry is aggregate only, so it cannot establish whether any particular source message fell inside cached input. A targeted recall probe recovered the decision **3/3**. Moving the original supporting message near the end or beginning also produced **3/3** recovery in each position, versus **3/3** in its original position. This rules against raw recall and position as the primary cause in these probes.

The deterministic runtime selected the exact original message `h03` (score **28**, `decision_context`), plus `v07-042` (**43.075**) and `v07-043` (**47.351**). `h03` is classified as `CURRENT DECISIONS` via explicit relationship metadata and remains valid; its metadata supersedes `h01`, not itself. The later messages are selected as `RELEVANT CONTEXT` and `CURRENT DECISIONS`. The exact `h03` sentence appears verbatim in the Working Context, alongside both later reaffirmations. The context contains the complete meaning—persistence, synchronization, separate layers, and independent replacement—and is not budget-excluded, deduplicated, or treated as stale. It occupies 3,737 returned tokens within the 4,000-token budget. The Working Context received **100%** coverage from the unchanged semantic evaluator in all three runs.

After correcting an incompatible Codex CLI flag combination (the first attempt failed before model execution), the unchanged `@Conceptualize` task was run three times. Each model invocation first made one fixture-rejected call with a shortened task argument, then retried with the exact frozen task and received the same 3,737-token context. The final answer included ARCH_02 in **1/3** runs and passed the full frozen rubric in **1/3**. The other two answers had 87.5% proposition coverage. This is not a retrieval or compilation loss: the host model did not consistently use a proposition that was explicitly delivered. The strict fixture server's exact-task check caused avoidable first-call retries; it is a harness integration friction, not a product runtime change.

**Classification:** Primary cause of the original repeated baseline omission: **C — synthesis/prioritization** (targeted recall succeeds while broad synthesis drops the fact). Secondary activated-condition failure: **H — model utilization** (Working Context is complete, but the final answer omits ARCH_02 twice). The fixture's exact-task guard adds secondary **I — host/integration friction** because it rejects shortened tool arguments before the successful retry. No code change was justified by this trace; the runtime already retrieves and preserves the fact. The capability improves ARCH_02 recovery from 0/3 to 1/3 here, but does not yet fix it reliably.

Machine-readable source positions, per-stage trace, scores, response/context evidence, targeted recall, position experiment, and activated runs are in [the ARCH_02 pipeline trace](results/v09-root-cause-pipeline.json), [targeted recall](results/v09-targeted-recall.json), [position diagnostic](results/v09-position-diagnostic.json), and [activated diagnostic](results/v09-root-cause-diagnostic-corrected.json). The incompatible CLI attempts are preserved and labeled invalid in [the failed invocation record](results/v09-root-cause-diagnostic.json).

## Post-fix context-utilization diagnostic (2026-09-29)

This was a later, separately recorded diagnostic explicitly authorized after the original 0/3 baseline gate. It does not retroactively change the original baseline or its conclusion that the planned primary A/B gate was invalid.

The diagnostic prompted two narrowly scoped changes without changing retrieval scores, context budget, sources, benchmark fixture, ground truth, or evaluator:

- Normal capability calls now treat `task` as a task description. The fixture MCP guard no longer compares it against the exact frozen prompt, so natural shortening/paraphrase is accepted.
- Working Context now separates binding critical constraints/current decisions from implementation state, prior work, supporting context, and superseded state. Deterministic priority rules place critical/required units first, retain full source wording, keep corroboration in traces without repeating duplicate text, and issue a compact directive: “Treat current decisions and critical constraints below as binding; do not omit or contradict relevant items.”
