# V0.5 — Generic context runtime and conversation source

V0.5 changes product positioning to model-independent context infrastructure while keeping the repository adapter and its dependency graph. It does not embed or call an AI model. The implementation adds a source-agnostic `ContextUnit`, a repository adapter, a structured conversation adapter, deterministic lexical conversation retrieval, bounded cross-source packing, per-session unit fingerprints, invalidation, and configurable token-cost estimation.

## Runtime behavior

`ContextUnit` carries an ID, source type and ID, optional parent, text, SHA-256 content fingerprint, version, token count, timestamps, relationships, and metadata. `RepositoryAdapter` exposes indexed files and code symbols as units; repository-only operations still use the existing graph-aware code path. `ConversationAdapter` emits conversation and message units and preserves role, order, timestamp, references, attachments, metadata, membership, adjacency, and reply links. The authenticated `POST /v1/context/conversations` endpoint replaces the provided conversation snapshot and avoids a revision bump for unchanged content.

The existing MCP tools accept optional `source_types` on map, search, expand, inspect, and pack. Conversation retrieval uses exact phrase and deterministic BM25-inspired lexical term weighting, ignores common stopwords, and can include one-hop related messages or repository units. Every generic candidate exposes its score, reason signals, token cost, known/invalidated state, and selected/omitted status in the existing trace. Lexical score is explicitly not semantic confidence. Repository-only dependency analysis remains specialized.

Session deliveries are keyed by unit ID, content hash, and disclosure level. Repeated unchanged content is referenced; a changed fingerprint is returned and identified as invalidated. Pack metrics separately report available, candidate, selected, previously supplied, unchanged, invalidated, newly delivered, and duplicate-avoided context tokens. These are context-string estimates, not host-model input telemetry.

`ModelPricing` accepts an explicit model name, pricing version, and rates for uncached input, cached input, and output. Cost is returned only when all three corresponding token measurements are known. No current provider rate or model token count is assumed.

## DETERMINISTIC RUNTIME TEST

The small fixture has four short histories and four questions covering a superseded storage choice, multiple runtime constraints, explicit exclusions, and a product-direction change. Each task compares the entire fixture history with a bounded runtime-selected context. Facts are checked by exact required-string coverage. This is a forced-context **runtime diagnostic**, not an agent response benchmark.

Raw paired records are in [v05-conversations.json](results/v05-conversations.json); rerun with `python -m conceptualize_evaluation.conversation_benchmark`.

| Measure | Full history control | Conceptualize selection |
| --- | ---: | ---: |
| Tasks with deterministic fact checks passed | 4 / 4 | 4 / 4 |
| Context string tokens delivered across the four tasks | 1,532 | 933 |
| In-process retrieval and pack time | not applicable | 2.55 ms average |
| Model-reported input/cached/output tokens | unavailable | unavailable |
| Estimated model cost | unavailable | unavailable |
| Host-agent operations / autonomous adoption | 0 / not applicable | 0 / not measured |

The selected-context strings totaled about 39% fewer context tokens for these fixtures while all checked fact strings remained present. The 2.55 ms value covers the in-process generic retrieval and pack operation only; it excludes MCP transport, database access, indexing, and any host-agent/model time. This does not show that an AI model would answer correctly, preserve constraints, spend fewer billed tokens, or adopt Conceptualize autonomously. The synthetic fixtures and exact-string checks are easy to solve and do not support general product claims. This remains separate from the real-model benchmark below.

## Single-problem real-model benchmark

The benchmark uses the frozen, synthetic 39-message Atlas field-inspection project history in [v05-conversation-problem.json](v05-conversation-problem.json). It includes separated decisions, a superseded localStorage proposal, offline/security/sync constraints, repeated details and unrelated planning noise. Every run receives the identical final question. The exact-term grading rubric and fixture hash were set before model runs and were not modified after answers were inspected.

The broken global Codex CLI installation was repaired by reinstalling `@openai/codex` with its matching Windows native package. The tested CLI was `codex-cli 0.157.1` on Windows x64 / Node.js 24.13.1. Models were selected through `codex exec --model`; both `gpt-6-sol` and `gpt-5.6-sol` completed authenticated smoke requests. These are only the tested exact IDs, not a claim that they are the only available models. Benchmark invocations used a fresh temporary `CODEX_HOME` and empty working directories to avoid unrelated user MCP servers, skills and project instructions. Model JSON events exposed input, cached-input, output and reasoning-output token fields.

Two repetitions were run for each model and primary condition, plus one separate forced-context diagnostic per model (10 real-model requests total). The model condition setting was low reasoning effort with the same Codex CLI and approval/sandbox controls. The primary results are:

| Model | Condition | Exact-rubric passes | Mean fact coverage | Mean model input | Mean output | Mean Codex elapsed | Adoption |
|---|---|---:|---:|---:|---:|---:|---:|
| `gpt-6-sol` | full history | 0/2 | 80.56% | 16,232 | 341 | 16.1 s | N/A |
| `gpt-6-sol` | Conceptualize available | 0/2 | 69.44% | 154,450.5 | 666.5 | 36.1 s | 2/2 |
| `gpt-5.6-sol` | full history | 0/2 | 83.34% | 15,375 | 356.5 | 13.0 s | N/A |
| `gpt-5.6-sol` | Conceptualize available | 0/2 | 0% | 19,312 | 128 | 10.6 s | 0/2 |

The rubric checks required architecture facts, constraints, superseded decisions, and the next step using frozen exact strings. Its coverage is a deterministic lexical measurement, not a semantic evaluator; phrase variants can produce false negatives. Every run failed at least one check and every model-condition cell had 0/2 strict passes. Do not interpret coverage alone as a correctness judgment.

In one primary cell, `gpt-6-sol` autonomously invoked `pack` with a 12,000-token budget. In the other, it invoked `map` and `expand`. Trace snapshots show delivered context strings of 1,173 tokens for the pack, and 841 + 1,296 tokens for map/expand. The direct pack candidate had 1,256 tokens and included 37 of 40 units, so it did not substantially reduce available history. `gpt-5.6-sol` did not invoke Conceptualize in either enabled run. Across primary runs, average model-reported input was 15,803.5 tokens in control and 86,881.25 with Conceptualize available. Average elapsed time was 14.51 s and 23.35 s respectively. These measurements include Codex orchestration and tool metadata and are not equivalent to raw context-string tokens.

The separate forced-context pack used 1,045 context-string tokens under a 1,200-token budget. Both models' forced-context answers failed the strict rubric (66.67% and 61.11% fact coverage). This indicates the current budgeted selection missed rubric facts; it is not a primary autonomous result.

No explicit versioned pricing snapshot was provided, so **ESTIMATED MODEL COST is N/A**. Agent-selected context tokens cannot be reliably aggregated for all enabled runs, and duplicate savings/session reuse were not directly linked to the model events; those fields remain unavailable. The local trace snapshots do record runtime stage timing. Persisted traces show a direct pack runtime of about 263 ms, including about 216 ms cache and 16 ms compilation, but this single request is not representative and excludes CLI/MCP startup and model latency. The full per-run matrix, rubric checks, trace snapshots and limitations are in [v05-model-matrix.json](results/v05-model-matrix.json); raw event logs and answers remain in the ignored local `evaluations/runs/` directory.

### Conclusion

This experiment does **not** show that Conceptualize let real models preserve correctness while processing less context or costing less. One model adopted the tool, but had higher average model input and latency with lower frozen-rubric coverage; the other did not adopt. The direct runtime pack returned nearly the complete conversation, while a smaller forced pack lost rubric facts. With two repetitions and a wording-sensitive rubric, the evidence is exploratory and supports no general performance claim.

## Validation and limits

The V0.5 implementation adds unit and authenticated API tests for source conversion, role/order/parent preservation, lexical search, source isolation, budgeted packing, session deduplication, content invalidation, and pricing telemetry validation. Repository indexing, Tree-sitter parsing, dependency relationships, Git metadata, and MCP tools remain in place. Historical V0.1–V0.4 reports were not rewritten.

Generic mixed-source retrieval currently uses lexical scores and explicit one-hop relationships. It is not a replacement for repository graph traversal, and document/tool-output/application-state adapters are not implemented. V0.5 made no dashboard redesign. Browser validation for this milestone is recorded in the release validation notes after the currently requested smoke checks.
