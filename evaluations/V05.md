# V0.5 — Generic context runtime and conversation source

V0.5 changes product positioning to model-independent context infrastructure while keeping the repository adapter and its dependency graph. It does not embed or call an AI model. The implementation adds a source-agnostic `ContextUnit`, a repository adapter, a structured conversation adapter, deterministic lexical conversation retrieval, bounded cross-source packing, per-session unit fingerprints, invalidation, and configurable token-cost estimation.

## Runtime behavior

`ContextUnit` carries an ID, source type and ID, optional parent, text, SHA-256 content fingerprint, version, token count, timestamps, relationships, and metadata. `RepositoryAdapter` exposes indexed files and code symbols as units; repository-only operations still use the existing graph-aware code path. `ConversationAdapter` emits conversation and message units and preserves role, order, timestamp, references, attachments, metadata, membership, adjacency, and reply links. The authenticated `POST /v1/context/conversations` endpoint replaces the provided conversation snapshot and avoids a revision bump for unchanged content.

The existing MCP tools accept optional `source_types` on map, search, expand, inspect, and pack. Conversation retrieval uses exact phrase and deterministic BM25-inspired lexical term weighting, ignores common stopwords, and can include one-hop related messages or repository units. Every generic candidate exposes its score, reason signals, token cost, known/invalidated state, and selected/omitted status in the existing trace. Lexical score is explicitly not semantic confidence. Repository-only dependency analysis remains specialized.

Session deliveries are keyed by unit ID, content hash, and disclosure level. Repeated unchanged content is referenced; a changed fingerprint is returned and identified as invalidated. Pack metrics separately report available, candidate, selected, previously supplied, unchanged, invalidated, newly delivered, and duplicate-avoided context tokens. These are context-string estimates, not host-model input telemetry.

`ModelPricing` accepts an explicit model name, pricing version, and rates for uncached input, cached input, and output. Cost is returned only when all three corresponding token measurements are known. No current provider rate or model token count is assumed.

## Deterministic conversation diagnostic

The small fixture has four short histories and four questions covering a superseded storage choice, multiple runtime constraints, explicit exclusions, and a product-direction change. Each task compares the entire fixture history with a bounded runtime-selected context. Facts are checked by exact required-string coverage. This is a forced-context **runtime diagnostic**, not an agent response benchmark.

Raw paired records are in [v05-conversations.json](results/v05-conversations.json); rerun with `python -m conceptualize_evaluation.conversation_benchmark`.

| Measure | Full history control | Conceptualize selection |
| --- | ---: | ---: |
| Tasks with deterministic fact checks passed | 4 / 4 | 4 / 4 |
| Context string tokens delivered across the four tasks | 1,532 | 933 |
| In-process retrieval and pack time | not applicable | 2.55 ms average |
| Model-reported input/cached/output tokens | unavailable | unavailable |
| Estimated model cost | unavailable | unavailable |
| Host-agent operations / autonomous adoption | 0 / not applicable | 0 / not measured |

The selected-context strings totaled about 39% fewer context tokens for these fixtures while all checked fact strings remained present. The 2.55 ms value covers the in-process generic retrieval and pack operation only; it excludes MCP transport, database access, indexing, and any host-agent/model time. This does not show that an AI model would answer correctly, preserve constraints, spend fewer billed tokens, or adopt Conceptualize autonomously. The synthetic fixtures and exact-string checks are easy to solve and do not support general product claims.

## Model matrix status

The Codex task-creation tool contract on this host advertises these configurations: `gpt-6-astra`, `gpt-6-sol`, `gpt-6-luna`, `gpt-5.6-sol`, `gpt-5.6-terra`, `gpt-5.6-luna`, and `gpt-5.5`. This list is configuration support, not evidence that a benchmark run occurred. The existing paired runner needs the Codex CLI, but the installed `codex --version` command fails before returning its version with `Missing optional dependency @openai/codex-win32-x64`. Consequently **zero of the requested 18 primary model runs and zero forced-context agent runs were executed**. No model was silently substituted or rerun. There are no per-model effectiveness, autonomous adoption, latency, model token, or pricing results to report. See [v05-model-matrix.json](results/v05-model-matrix.json) for the explicit unrun cells and the captured CLI failure.

The runtime-only diagnostic above does not fill those cells. To complete the agent comparison, a reproducible harness must provide the same agent/client and task context in enabled and disabled conditions, and expose per-run model identity plus input, cached-input, and output telemetry. Until then, comparisons such as a higher-capability model with full context versus a lower-cost model with Conceptualize remain untested.

## Validation and limits

The V0.5 implementation adds unit and authenticated API tests for source conversion, role/order/parent preservation, lexical search, source isolation, budgeted packing, session deduplication, content invalidation, and pricing telemetry validation. Repository indexing, Tree-sitter parsing, dependency relationships, Git metadata, and MCP tools remain in place. Historical V0.1–V0.4 reports were not rewritten.

Generic mixed-source retrieval currently uses lexical scores and explicit one-hop relationships. It is not a replacement for repository graph traversal, and document/tool-output/application-state adapters are not implemented. No dashboard flow was tested for this milestone. No browser was opened.
