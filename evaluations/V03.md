# V0.3 runtime and evidence

V0.3 adds `conceptualize_inspect`, compact cost manifests, deterministic context IDs, automatic incremental file refresh, stale-context notices and per-stage timings. Five existing tools remain compatible. Session deltas and structural scoring continue to drive bounded source selection. No model runs inside Conceptualize, and the dashboard layout and PostgreSQL/Redis architecture are retained.

## Actual host-agent evidence

All ten original tasks were rerun in both modes with the same gpt-6-sol model, CLI, task prompts and fixture commits. All twenty isolated attempts passed independent checks and repository tests. Control averaged **80.362 seconds**; Conceptualize-available averaged **102.846 seconds**. Observed unique-file sums were **22 versus 30**, with **one versus zero** supported repeated reads. These are incomplete command-derived lower bounds, not total filesystem measurements.

**No V0.3 cold-suite or warm-sequence agent invoked MCP.** Compiled Conceptualize context delivered was therefore zero. Tool availability and startup do not establish a scoring, inspection or session-memory effect. These runs do not demonstrate a speed improvement or reduced exploration.

## Runtime scale and overhead

Scripted real stdio MCP clients measure 60-, 400- and 2,000-Python-file fixtures with known synthetic consumers. Each cold/warm condition performs four related inspect requests, including a repeated target and a file change. This is **protocol and structural coverage evidence, not an agent usefulness benchmark**. Warm duplicate avoidance is measured; token reduction alone does not establish utility.

The first isolated 2,000-file profile failed all eight calls. A reproduced quadratic filename/test scan cost **72,128 ms** in direct graph construction. Indexing test names reduced that measurement to **184 ms**, preserving the exact graph edge hash at all three sizes. Full scans of unchanged source bodies are avoided; incremental refresh still walks file metadata and rebuilds the graph snapshot.

MCP projection retains every stale ID and every selected item's score explanation, bounds the relationship preview, and references complete omitted-candidate and relationship evidence in persisted traces. This reduced the 400-file change response from **9,041,422 to 249,151 bytes** in separate profiles. Full trace provenance remains available. Earlier and later cohorts are preserved, not overwritten.

[Graph before](results/v03-graph-before.json), [graph after](results/v03-graph-after.json), [protocol before](results/v03-scale-before.json), [intermediate protocol after](results/v03-scale-after.json) contain actual measurements. Indexed relationship lookups subsequently reduced direct 2,000-file compilation from 10,244 to 5,378 ms, preserving the combined hash of context, scores, manifest, delivery IDs and deltas. The [final 24-call profile and all nine stage percentiles](results/v03-scale-release.md), [final data](results/v03-scale-release.json), records zero errors; high-fanout 2,000-file calls still take roughly 8–13 seconds. P50/P95 use nearest rank, with sample and missing counts. Transport is an HTTP client residual including serialization/authentication, not pure wire or stdio latency. Stage timers are approximate and overlap. SQLite and deliberately unavailable Redis are QA conditions; failed-cache timing is not normal Redis performance.

The full ten-task agent cohort preceded these performance-only optimizations. Its recorded source hash is retained. No optimized-agent speed claim is inferred from protocol profiles or equivalent graph hashes.

## Answers supported by the evidence

1. **Where does it help?** V0.2 slug recovery supplied subsequently changed source/test files before their supported independent reads. This is bounded observed discovery evidence, not a general task-category advantage. V0.3 agent utility is unmeasured because tools were not invoked.
2. **Where does it add overhead?** V0.2 broad maps and packs after manual reads produced redundant exploration flags. V0.3 availability runs were slower and surfaced no MCP context. High-fanout synthetic inspect requests expose concrete runtime scaling costs.
3. **How much is runtime overhead?** Stage percentiles and raw round trips quantify it on the measured fixtures. Graph and metadata bottlenecks were reproduced and optimized. Production infrastructure overhead remains unmeasured.
4. **How much is additional agent behavior?** Available events show command/search sequences and buffered tool-wait spans. Model idle time and a causal decomposition of the completion gap remain unknown. With zero calls, V0.3's elapsed gap cannot be assigned to scoring/packing operations.
5. **Does inspect reduce round trips?** One actual SDK call returns manifest, structure, dependencies, consumers, tests and bounded source. The protocol supports consolidation; autonomous agent round-trip reduction was not demonstrated.
6. **Does session context become more valuable?** Repeated scripted requests avoid unchanged delivery and invalidate stale IDs after edits. Warm agents made no calls, so useful task-level savings remain unproven.
7. **Does utility increase with scale?** Synthetic consumer relationships are structurally discovered at all tested scales; source remains budgeted. Costs increase with fanout. Neither these fixtures nor zero-call agent runs establish greater product utility in large real repositories.
8. **What does the host repeatedly need?** Existing traces show dependency/consumer/test relationships and implementation source requests, sometimes arriving after manual exploration. Inspect exposes that environment together. Efficient delivery is demonstrated mechanically; superior host navigation is not established.

## Reproduce

Use a dedicated API/database for each benchmark family. Existing output directories are rejected to preserve evidence. Run from the repository using its configured Python environment; API/database environment variables must match.

```powershell
.venv/Scripts/python.exe -m conceptualize_evaluation.suite run --output evaluations/runs/new-cold --codex <codex.exe> --model gpt-6-sol --api-url http://127.0.0.1:8059 --workers 2 --timeout 600
.venv/Scripts/python.exe -m conceptualize_evaluation.session_benchmark --output evaluations/runs/new-sessions --codex <codex.exe> --model gpt-6-sol --api-url http://127.0.0.1:8079
.venv/Scripts/python.exe -m conceptualize_evaluation.protocol_benchmark --output evaluations/runs/new-scale --api-url http://127.0.0.1:8069 --report evaluations/results/new-scale
.venv/Scripts/python.exe -m conceptualize_evaluation.diagnose evaluations/runs/new-cold --output evaluations/results/new-diagnosis
.venv/Scripts/python.exe -m conceptualize_evaluation.version_report --v02 evaluations/runs/runtime-suite-v1 --v03 evaluations/runs/new-cold --output evaluations/results/new-comparison
```

The existing trace panel displays scores, deltas, manifests, invalidation and interaction patterns without redesign. Desktop and mobile trace flows passed with no console/page errors; the 1589×990 desktop overview remains one viewport. Validation: 61 Python tests, 4 frontend tests, lint, TypeScript checking and production build passed. Real stdio SDK integration exercises all six tools.
